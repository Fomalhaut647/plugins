# 会话收尾

1. 整理文档：把本会话改动涉及的文档改到和代码一致。
2. 提交本会话的改动并推送。本会话开过子会话的（`list_sessions` 传 `{"linked": true}` 查），先把它们的改动收进来：还在跑的等它结束；在自己工作树里改的，把它的分支合进本会话的分支，调用本 skill 就算用户同意合并；直接改在本工作区的，算本会话的改动。在功能分支上就开 PR，用 `gh pr checks --watch` 在本轮里等 CI 跑完，不要结束本轮或交给 Auto-fix 去等：CI 失败就自己修好再推，通过后合并进 main，合并后把主工作区的 main 也快进到最新；在 main 上就直接推送。处理好 git 状态，直到工作区干净。不属于本会话的改动不要提交，也不要丢弃。
3. 关闭本会话修复的 issue：只关本会话明确在修、修复已经进了 main 的，用 `gh issue close` 附一句评论注明修复所在的 PR 或提交。没修完的不关，在报告里说明。
4. 简要报告做了什么，然后用 `archive_session`（传 `"self"`）归档本会话。还有要用户处理的事时不归档，在报告里说明。

## 合并前审查

用户要求合并前 review 时，在第 2 步推送合并之前先审查：

- 用 `start_session` 开子会话（`initiation: "user_asked"`，`use_worktree: false`），让它用 code-review 只读审查 `origin/main...HEAD` 的改动，最后一条回复用文字列出全部发现，每条标明大、中、小。告诉用户一声即可，不用等批准。
- 子会话结束后，用 `list_events` 读它的完整结果，逐条核实，只修大 bug；中小 bug 列进报告，由用户决定。
- 用户强调多轮审查时，修完再开新的子会话审，直到某一轮没有大 bug。

大 bug 指正常使用就会出错：结果错、功能不可用、崩溃、丢数据、有安全漏洞，或者把原本正常的行为改坏。
