# 需求分析：需求侧与供给侧

把一个产品设想转化为可检验的需求判断，回答「为谁、在什么情况下、解决什么动机」「赢在哪个关键要素」「为什么现在」「为什么是我们」。不要把分析写成产品功能清单，也不要擅自把用户已选定的产品换成另一门生意。

本方法依据《2026-09-19_需求分析课_v4.pdf》前半部分及用户提供的思维导图。课程来源、页码与案例边界见 [课程依据](references/course-notes.md)。证据标记、工作表和验证设计是本 skill 的操作化约定，不冒充课件原文。

## 核心口径

**需求 ＝ 用户 × 场景 × 动机。** 这里的乘号表达三个条件的组合，不是数值乘法；任一条件改变，都要重新检查需求和替代方案。

- **用户**：先用可识别的现实身份、生活阶段、职业或组织角色描述人群，例如应届求职生、退休老人、企业 HR。偏好、技能和预算可以继续细分，但「喜欢某产品的人」不能替代用户本身，也不要只写「所有人」。
- **场景**：写清触发事件、所处环境、时间窗口和可用时长；按实际决策需要补充设备、是否可中断、是否有人在场等约束。「有空时」「工作中」通常不足以区分方案。
- **动机**：写用户希望得到的结果，例如放松解闷、把朋友招待好、提高本场面试通过概率；不要写成「使用 AI」「玩某种游戏」「看短视频」等解决方案或行为。

一次先分析一个明确组合。多个组合可以并列比较，但不要把不同组合的要素、竞品和证据混成一个结论。分析产品不等于否定产品：先区分需求与方案，再判断这个方案是否更好地满足需求。

## 按问题深度执行

完整分析覆盖下述两侧；局部追问只展开相关部分，并沿用已经确认的需求边界。资料缺失时，给出带标签的初步假设或提出会改变判断的关键问题，不用连续追问阻塞所有分析。

### 一、需求侧分析

**1. 需求本质。** 从用户给定的设想或材料写出一句话：

> 〔明确用户〕在〔具体场景与时间约束〕下，希望〔主要动机〕，因此存在〔不绑定特定产品的需求〕。

不清楚该选哪种人群或场景时，用「固定两项，只改变一项」对比候选组合。记录当前替代方案和不使用该产品时的做法。

**2. 需求侧要素。** 找出满足该需求的关键体验条件，并区分课程中的四类：**底线要素、够用就好、越多越好、惊喜要素**。分类没有统一标准，必须结合这个用户与场景说明理由；不能把所有功能都列为关键要素。

针对真正决定选择的要素，说明用户如何感知好坏、现有方案做到什么程度、有什么突破性解决方案。把「体验结果」与「实现手段」分开，例如「像真实面试一样被深入追问」是体验，语音 API 或数字人是候选实现。

把竞品放在同一套关键要素上比较。竞品包括同类产品、跨形态方案、人工服务、自行解决等实际替代者，不限于名字里带 AI 的公司。回答竞品在哪些要素发力，以及用户从现方案换到新方案的成本；必要时再看用户离开新方案的成本。未知项写未知，不把「未见证据」当作「竞品没有」。

从比较中提出重点突破的要素及取舍。课程的「10 倍好」用于追问突破幅度，不意味着每个要素都应做到十倍，也不能在没有基准和测量时声称已经十倍好。

**3. 需求侧变化。** 检查用户、场景、动机或对关键体验的重视程度是否真的改变。区分长期存在的需求与近期变化；写出变化前后、发生时间、证据以及它怎样改变选择或付费。可以得出「未发现明显变化」。不要用「AI 火了」替代需求变化。

**4. 需求大小的接口。** 本 skill 只界定待测需求、统计对象和边界，不自动展开完整规模测算。用户同时问「能做多大」时，将这些定义传给可用的 `aiic:market-sizing`；另一份 skill 不可用时，也能单独交付本分析。不得把体验关键要素中的「强压力感」「有用」直接当成市场规模的货币强度。

### 二、供给侧分析

**1. 供给侧要素。** 沿「关键体验 ← 交付能力 ← 所需资源与组织」反向分析。只纳入影响上述关键体验的供给条件，而不是堆砌完整技术栈。

将供给要素分为 **可能构成壁垒** 与 **不构成壁垒但仍然关键** 两类。对壁垒候选说明：凭什么难复制、我们是否实际拥有或能获得、竞争者如何追赶、可能持续多久、还缺什么证据。把已拥有的优势、可建立的优势和纯设想分开。

公共 API、普遍可获得的低成本能力可能打开机会，但不能仅因关键就称为我们的壁垒。也不要反过来把它们排除出供给分析。课程特别区分「可购买的实时语音 API」与「端到端流畅的音视频工程体验」；后者即使有差距，也不自动成为长期壁垒。

**2. 供给侧变化。** 检查能力、成本、交付方式、内容供给或组织条件的变化。指出哪个瓶颈现在跨过了什么门槛，如何使某个关键体验或经济条件成立。短期领先、长期壁垒和普惠性条件变化是不同判断。

**3. 合并回答 Why NOW / Why ME。**

- **Why NOW**：同时检查需求侧和供给侧。写清真正的变化及因果链，允许仅一侧变化、两侧变化，或暂时没有足够证据。
- **Why ME**：落到本团队相关的、已有或可建立的难复制能力。没有团队资料或壁垒证据时，明确结论未成立，并列出验证路径；不要从「市场需要」直接跳到「我们能赢」。

## 转为研究与 MVP

**用户调研的关键是挖掘需求本质和关键要素；MVP 的关键是验证关键要素的解决方案成立。** 把结论落到最影响决策的未知量，而不是默认开发完整产品。

用「假设 → 要问/要观察什么 → 最小验证 → 成功与失败的判据 → 结果如何改变决策」连接调研与试验。访谈、行为、交易、使用日志各自支持什么结论要分清；口头喜欢不等于实际使用或付费。量化门槛须标明是预设的决策标准，不得伪装成已测得结果。

需要完整交付、访谈问题、MVP 工作表或与规模测算衔接时，使用 [分析工作表与逐步示例](references/analysis-workbook.md)。不要为了填表强行给所有项目相同评分或固定权重。

## 证据和交付

区分 **材料/数据明确支持的事实、分析推断、待验证假设**，让重要判断能回溯到具体材料、访谈或来源。课程案例是教学材料，不是对今天产品能力、价格、市场状态的背书。实际项目涉及当前竞品和技术变化时，使用可用的检索工具查证；不能检索就保留未知，不拿课堂数字顶替实测。用户限定只依据材料时，不引入外部事实。

通常交付：明确的需求定义、关键要素与替代方案比较、两侧变化、供给壁垒判断、核心结论和下一步验证。可附一句突出关键价值的产品介绍，但把它与需求定义分开。完整报告保留「需求侧 / 供给侧」结构；简短问题不必输出全部表格。

交付前检查：需求是否脱离产品名仍成立？竞品是否来自同一需求？体验和供给是否混淆？公共能力是否被误判为独占壁垒？Why NOW 是否真的说明变化？Why ME 是否有团队依据？结论是否区分已验证与假设？
