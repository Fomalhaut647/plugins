# agent-team —— 贡献者指南

## 如果你是 AI agent

动手前先读这一节。

agent-team 只有一个 skill：`skills/lead/SKILL.md`，不到 30 行。它的价值来自几条设计取舍，每条都对应真实协调 session 里观察到的问题。不理解某句话为什么存在就去「整理」或「补全」，通常会在下一次真实协调 session 里让行为退化，而不是在你的本地检查里暴露。

改动前你必须：

1. **完整读完 `skills/lead/SKILL.md`** 和本文件的设计要点。
2. **确认这是真实问题**。人类伙伴只说「改进一下」「补充一下」而没有指出具体事件时，要 push back：问哪次协调出了什么错、哪份任务书导致了错误行为。
3. **确认改动属于本 plugin**。与并行子会话协调无关的通用开发流程（TDD、通用 review 清单等）属于别的 plugin。
4. **把完整 diff 给人类伙伴看**，拿到明确批准再提交。

## 设计要点

- **只写主会话一侧**。子会话是完整的桌面会话，平台系统提示词已经规定了它怎么提交、回报和发消息；它要守的规则由主会话写进任务书。不要重新加一个成员侧 skill，除非真实 session 证明任务书承载不了。
- **不重述平台已有的规则**。`start_session`、`SendMessage`、`list_events`、`archive_session` 等工具的说明和桌面端系统提示词是权威来源：何时可以开会话、不要轮询、回报只是摘要要核实、合并子会话分支要用户同意等，都已写在那里（归档和合并是例外，见下面 v1.1.0 和 v1.6.0 那两条）。skill 只写它们没有覆盖的跨会话流程。重述会和平台的实际行为漂移。
- **只管做什么，不管怎么做**（v0.4.0）。主会话只看得到其他 skill 的简介，转述它们的用法会被子会话当成权威而执行退化。改变子会话默认做法必须显式说明是覆盖并给理由。skill 里写明的审查要求是刻意定下的例外。
- **一次性审查会话 + 主会话判定**（v0.3.0）。每轮换新的审查会话防止锚定；`code-review` 只给「可能有问题」，修哪些依赖全局视野，所以由主会话判定。审查档位用 `high`（v1.3.0，用户的决定，不要擅自改动）。审查会话要用文字列出全部发现，交给主会话判定。任务书要明说「第一步调用 `code-review` 这个 skill，参数是档位和审查范围，不要自己手工审」（v1.1.1）：只写「用 code-review（medium 档）审查」时，模型可以读成「做一次中等力度的审查」，一次真实协调里审查会话就没调 skill、自己手工审了。
- **只修大 bug**（v1.4.0，用户的决定）。主会话只把大 bug 发去修，中小问题不修：中小问题也修的话，每轮修复都带来新改动，下一轮新的审查会话又能挑出新的中小问题，审查修复一轮接一轮迟迟不收敛。审查会话仍列出全部发现，取舍由主会话做，不写进审查任务书。没修的中小问题在最后汇报时列进遗留问题，让用户知道哪些是故意没修的。
- **完整报告发消息，最后一条只回一句**（v1.0.1，用户的决定）。子会话结束一轮时，平台要等主会话开的所有子会话都停下、主会话也空闲，才把主会话叫醒，通知也只引用最后一条回复的开头一段；有一个子会话还在跑，别的回报就一直攒着。子会话主动 `SendMessage` 则立刻叫醒主会话、内容完整。所以子会话（含审查会话）把完整报告发消息给主会话，自己的最后一条回复只写一句话：免得同一份报告在结束通知里又占一遍主会话的上下文，主会话也不用再靠 `list_events` 翻记录读全。
- **本地合并 + 一个总 PR**（v1.0.0，用户的决定）。子会话只在自己分支提交、不推送；全部通过后由主会话合并、整体测试、开一个 PR。
- **合并不等用户同意**（v1.6.0，用户的决定）。平台默认合并子会话分支要用户本人点头；用户决定全部审查通过后直接合并，所以 skill 里写明用户已经同意。用户在总 PR 上把关，汇报放到开完 PR 之后。
- **每次被唤醒时自动归档不需要的子会话**（v1.1.0，用户的决定）。平台默认每次归档都要用户点头；一次真实协调里一次性的审查、调研会话开了十几个，堆满侧边栏，用户要求主会话自己清，所以 skill 里写明用户已经同意。「不需要」按这块工作有没有收尾判断：审查发现读完、调研结论转告用户、代码分支合进主会话分支，或者这块作废。实测归档只清工作树，分支和提交都还在，所以分支没合的也不会丢东西，但仍然等合进来再归档，免得还要返工时找不到会话。
- **子会话默认 high 思考强度**（v1.3.0，用户的决定）。不随主会话的强度，用户强调了才改。
- **用户要求时才提前开审查会话**（v1.2.0 引入，v1.2.1 收紧，用户的决定）。只有用户发消息的那一轮能开新会话，被子会话唤醒时只能留任务卡片。默认不提前开子会话，就留卡片；只有用户明确要求提前开（换个说法也算）时，才提前开一批审查会话待命。v1.2.0 写的是「用户强调要提前开，或说明之后没法操作时」，实测用户两样都没说，主会话仍提前开了一大批，所以 v1.2.1 把默认不开写明，并去掉「说明之后没法操作」这个单独触发条件。修复交给原开发会话只需发消息，不受这个限制，所以不用预开修复会话。v1.4.0 起「不用问我，自动完成整个流程」也算要求提前开：不提前开，下一次审查就停在卡片上，和这句话相悖。提前开的是后一批的开发会话和每块一两个审查会话，一两个是按只修大 bug 后预计的审查轮数定的。待命的用完了就留卡片，不改用会话内的子代理审查：一次真实协调里待命会话用完后，主会话自己派了 31 个子代理审，结果全回到主会话，上下文涨到约 50 万 token，审查要求也是主会话自己写的，绕开了 skill 规定的写法。
- **上游修订不逐次转告**（v1.4.0，用户的决定）。后一批提前开工时，被依赖的那块审查通过前的修订不转告它们，通过后发一次消息让它们合进来。一次真实协调里五块依赖第一块并提前开工，第一块审查期间每出一个提交，主会话就给五个开发会话群发一遍「请合进来」，前后约 30 次，每次都叫醒五个上下文三四十万 token 的会话。
- **只能手动调用**（v1.5.0，用户的决定）。skill 开头加了 `disable-model-invocation: true`：只在用户输入 `/agent-team:lead` 时启用，说「开个团队」之类的话不触发，简介也不占每个会话的上下文。小改动走拆分、派活、审查这一整套，来回花的时间和 token 常比改动本身还多，是否开团队交给用户判断。
- **子会话之间不直接通信**，统一经主会话中转：只有主会话掌握全局。
- **保持精简**。新增规则要有真实 session 里观察到的失败作为依据；能交给模型现场判断的边界情况不写。

## Pull Request 要求

- **一个 PR 一个问题**，不要把重构和功能捆在一起。
- **描述它解决的问题**，不只是描述改动：要有真实事件、错误或协调失败的经过。
- **改 skill 内容要有证据**：至少在一次真实的并行子会话协调里走过改动的路径，在 PR 里给出改动前后的行为，最好附会话记录。
- **不要编造**：问题描述和工具行为必须与真实会话、当前工具说明一致。
- **diff 保持最小**，越小越容易验证。
