# agent-team —— 贡献者指南

## 如果你是 AI agent

动手前先读这一节。

agent-team 只有一个 skill：`skills/lead/SKILL.md`。它的价值来自几条设计取舍，每条都对应真实协调 session 里观察到的问题。不理解某句话为什么存在就去「整理」或「补全」，通常会在下一次真实协调 session 里让行为退化，而不是在你的本地检查里暴露。

改动前你必须：

1. **完整读完 `skills/lead/SKILL.md`** 和本文件的设计要点。
2. **确认这是真实问题**。人类伙伴只说「改进一下」「补充一下」而没有指出具体事件时，要 push back：问哪次协调出了什么错、哪份任务书导致了错误行为。
3. **确认改动属于本 plugin**。与并行子会话协调无关的通用开发流程（TDD、通用 review 清单等）属于别的 plugin。
4. **把完整 diff 给人类伙伴看**，拿到明确批准再提交。

## 设计要点

- **只写主会话一侧**。子会话是完整的桌面会话，平台系统提示词已经规定了它怎么提交、回报和发消息；它要守的规则由主会话写进任务书。不要重新加一个成员侧 skill，除非真实 session 证明任务书承载不了。
- **不重述平台已有的规则**。`start_session`、`SendMessage`、`list_events`、`archive_session` 等工具的说明和桌面端系统提示词是权威来源：何时可以开会话、不要轮询、回报只是摘要要核实、合并子会话分支要用户同意等，都已写在那里（归档和合并是例外，见下面 v1.1.0 和 v1.6.0 那两条）。skill 只写它们没有覆盖的跨会话流程。重述会和平台的实际行为漂移。
- **只管做什么，不管怎么做**（v0.4.0）。主会话只看得到其他 skill 的简介，转述它们的用法会被子会话当成权威而执行退化。改变子会话默认做法必须显式说明是覆盖并给理由。skill 里写明的要求（先交验收清单、先写会失败的测试再做最小修改、审查第一步调用 `code-review`，以及 `codex.sh` 给 Codex 任务书追加的固定规矩）是刻意定下的例外。
- **完成看验收清单，审查不当终点**（v2.0.0，用户的决定，取代 v0.3.0 起「反复审到没有值得修的为止」的循环）。依据 2026-10-29 两次真实协调（A 线 5 张卡、C 线 6 张卡）：新开审查会话 18 轮和 20 轮，发现 168 条和 162 条，修了 135 条和 100 条，没有一块是因为审查报不出严重问题而结束的，都是主会话自审拍板收尾，C 线的收尾时机跟着待命审查会话还剩几个走。根子在审查工具：审查会话里跑的 `code-review` high 档写明召回优先、宁可多报、不复核、目标至少 5 条、最多 10 条，C 线 20 轮里有 10 轮正好报满 10 条，「审到没有严重问题」永远到不了。现在一块做完，看开工前定下的验收清单是否都被自动测试证明；审查只找清单漏了什么、哪条没测到。
- **每块只审一次，按固定标准分拣**（v2.0.0，用户的决定，取代 v1.4.0 的「只修严重 bug」）。第 1 轮审查选中的几乎都是真缺陷（A 线 39 条里 38 条）；第 2 轮起选修的问题里，出自上一轮修复或同类没修全的，A 线占 74%，C 线占 90%（60 条里原始缺陷只有 3 条）。v1.4.0 让主会话凭感觉挑「严重」的，口径每轮在漂，C 线每轮选修比例从 20% 到 100%，选了 23 条审查者自己标为低、中低或清理类的问题，却放过了运行循环第 1 轮的两条「中」。所以一块只开一次审查会话，之后不再为修复开审查；分拣只认四类：挡合并（违反清单、碰红线、有具体出错场景的丢数据泄密主流程坏，以及清单里没真正测到的条目）、设计问题、误报、其余（全进遗留 Issue，这一轮不修）。审查报多少条都不再拉长循环，所以档位仍用 `high`（v1.3.0，用户的决定，不要擅自改动）。档位和下面两句只管 Claude 审查会话；v4.0.0 起审查默认交给 Codex，见后面「默认开发用 Claude、审查用 Codex」那条。任务书要明说「第一步调用 `code-review` 这个 skill，参数是档位和审查范围，不要自己手工审」（v1.1.1）：只写「用 code-review（medium 档）审查」时，模型可以读成「做一次中等力度的审查」，一次真实协调里审查会话就没调 skill、自己手工审了。待命的审查会话开场时还没有这块的分支，所以要先把工作树切到这块分支的最新提交再审。
- **先交验收清单再写代码，产品问题开工前问用户**（v2.0.0，用户的决定）。两次协调里，没定下来的设计都是在修复循环里边修边定的：「门户只在同学在场时读」被审查一步步升级成防进程内的恶意代码，A5 为此连续 4 轮约 8 条，最后改到了地基；C4 的验收标准里没有威胁模型，网址核对成了无穷枚举，修到第 5 轮才承认认法永远穷尽不了；C 线 18 个修复提交里 15 个同时改了设计文档，这些会改变产品行为的决定没有一件问过用户。所以开发会话的第一件交付物是验收清单（看得见的行为、适用的红线、明确不管什么、拿不准的产品问题），主会话核对后才写代码，产品问题汇总一次问用户。用户说过不用问时按建议定、最后列出供否决，和用户全局规则里「中途不要停下来问我」的处理一致。
- **小修，用测试复核；整类修法单独排期**（v2.0.0，用户的决定，取代 v1.7.0 的「小修复由主会话复审」和 v1.8.0 的「整类堵上，复审只看修复」）。v1.8.0 加了「整类堵上」后，主会话把单条发现写成「每一个失败出口」「所有异常类型」，还常直接指定新方案（C 线 20 份修复要求里 15 份写了整类堵上），修复变成了重新设计：C4 五轮修复约 1900 行（含测试），比它最初的开发约 1400 行还多；第 1 轮修复新建的两处机制，吃掉了后四轮选修 24 条里的 21 条。有研究也发现，让模型连续 5 轮「改进」代码，严重漏洞反而多了 37.6%。所以修复要求只写问题和出错场景，开发会话先写修复前会失败的测试再做最小修改；复核看测试和改动范围，不开审查会话；要整类重做、改到地基或别的块的，排成单独一块走完整流程。修复的代码由整合审查独立看一次。
- **预算和熔断**（v2.0.0，用户的决定）。原来的循环只有「直到没有严重 bug」这一个终止条件，而这个条件够不着；A 线用户听到「还要 2.5～3.5 小时」后直接叫停了 3.5 小时。现在每块审查一次，修复最多两次：第二次只来自第一次复核没过（测试没过、改动越界、修法对不上出错场景），不来自再审；第二次复核还没过就停下这块，按卡住的原因（设计没定、修法要动结构、开发会话修不动、问题本身站不住）带选项找用户。用户说过不用问时的默认：碰红线的绝不原样合并（关掉功能或这块不合），不碰红线的记高优先级遗留问题照常合。同一块第二次熔断就移出这次任务，保证整次任务一定能收尾。
- **整合审查只看块间衔接和修复**（v2.0.0，用户的决定）。C 线 20 轮块内审查一条也没报出块与块交界处的问题，整合审查查出 2 条，端到端测试又修掉 3 个真问题。修复的代码在新流程里不单开审查，也放到这一次一起看，这样每段代码恰好被独立审查一次。整合的修复 v3.4.0 起交给整合修复会话，见下一条。
- **整合的修复交给预开的整合修复会话，开发会话通过即归档**（v3.4.0，用户的决定，取代 v2.0.0 的「整合的修复仍交给原开发会话」）。用户在真实协调里看到：开发会话的块通过审查后一直闲置，等整合审查查出问题交回去修时已闲置一个多小时，提示缓存过期，叫醒要重写整份长上下文。保活都比换会话贵：开发会话自己定时心跳，每结束一轮都会叫醒主会话，一次心跳读两份大上下文；主会话定时去叫醒更糟，一次心跳叫醒主会话两次；心跳还要对每个开发会话付费，而整合审查通常只牵涉一两块。缓存保住了也得在几十万 token 的上下文里修，每次模型调用都重读一遍，比新会话读几个相关文件贵。衔接问题常横跨两块，原开发会话各自只熟悉一侧，一个在合并后的分支上修的会话更合适，也省掉把各块的修复再合并一遍。以往整合阶段挡合并的问题很少（C 线整合审查 2 条、端到端测试 3 条），一个会话做得过来。被子会话唤醒的那一轮开不了新会话，所以它在开工时预开待命（审查由 Claude 做时，整合审查会话也一样）。开发交给 Codex 时同理，新开一个 Codex 会话修；Codex 随时能启动，不预开。
- **完整报告发消息，最后一条只回一句**（v1.0.1，用户的决定）。子会话结束一轮时，平台要等主会话开的所有子会话都停下、主会话也空闲，才把主会话叫醒，通知也只引用最后一条回复的开头一段；有一个子会话还在跑，别的回报就一直攒着。子会话主动 `SendMessage` 则立刻叫醒主会话、内容完整。所以子会话（含审查会话）把完整报告发消息给主会话，自己的最后一条回复只写一句话：免得同一份报告在结束通知里又占一遍主会话的上下文，主会话也不用再靠 `list_events` 翻记录读全。
- **本地合并 + 一个总 PR**（v1.0.0，用户的决定）。子会话只在自己分支提交、不推送；全部通过后由主会话合并、整体测试、开一个 PR。
- **合并不等用户同意**（v1.6.0，用户的决定）。平台默认合并子会话分支要用户本人点头；用户决定全部审查通过后直接合并，所以 skill 里写明用户已经同意。用户在总 PR 上把关，汇报放到开完 PR 之后。
- **每次被唤醒时自动归档不需要的子会话**（v1.1.0，用户的决定）。平台默认每次归档都要用户点头；一次真实协调里一次性的审查、调研会话开了十几个，堆满侧边栏，用户要求主会话自己清，所以 skill 里写明用户已经同意。「不需要」按这块工作有没有收尾判断：审查发现读完、调研结论转告用户、开发会话在这块通过后（v3.4.0 起整合的修复不再交回原开发会话）、整合修复会话在整合审查通过后，或者这块作废。实测归档只清工作树，分支和提交都还在，所以块通过后、合并前就归档也不会丢东西。
- **子会话默认 high 思考强度**（v1.3.0，用户的决定）。不随主会话的强度，用户强调了才改。交给 Codex 的开发和审查，原先模型和思考强度跟用户的 Codex 设置（v3.0.0），是否开 Fast 模式也一样（v3.1.0，用户的决定）；v4.0.0 起默认用 gpt-6.1-sol、xhigh、开 Fast 模式（用户的决定），用户这次指定了就按用户的。默认值写在 SKILL.md 里、由主会话分派时传给 `codex.sh`，脚本本身不写死：不传时它仍沿用用户的 Codex 设置。
- **开工时一次开好全部会话，待命的不预读**（v2.0.0，用户的决定，取代 v1.2.0～v1.2.1 的「用户要求时才提前开」）。只有用户发消息的那一轮能开新会话，被子会话唤醒时只能留任务卡片；两次协调里用户最后都要求了提前开，C 线在那之前点了 7 张卡片，最后一张等了 11 小时才被点开。轮数有上限后，要用多少会话开工时就算得出（每块一个开发、一个审查，加一个整合审查，v3.4.0 起再加一个整合修复；v4.0.0 起审查默认交给 Codex，不开审查会话），所以一次开好。块内的修复交给原开发会话只需发消息，不用为它预开修复会话。待命会话什么都不读：实测它们闲置 2～16 小时后被叫醒，只重写约 2 万 token 的缓存（约 5 万的公共部分仍命中），和那时新开一个会话一样，提前开不多花钱。开好的不够用时留卡片，不改用会话内的子代理：一次真实协调里待命会话用完后，主会话自己派了 31 个子代理审，结果全回到主会话，上下文涨到约 50 万 token，审查要求也是主会话自己写的，绕开了 skill 规定的写法。
- **后一批等依赖的块通过后再开工**（v2.0.0，取代 v1.4.0 的「上游修订不逐次转告」）。v1.4.0 那次协调里五块依赖第一块并提前开工，第一块审查期间每出一个提交，主会话就给五个开发会话群发一遍「请合进来」，前后约 30 次，每次都叫醒五个上下文三四十万 token 的会话。现在上游的审查修复有上限、很快结束，下游等它通过再从它的分支切出，就没有转告这回事，也不会有长上下文会话干等。
- **长上下文会话闲置超过一小时，换新会话接手**（v2.0.0）。会话的提示缓存一小时过期。A 线用户暂停 3.5 小时后，四个开发会话恢复时各重写了 51～67 万 token 的缓存，按 Opus 5.5 的 API 价每个约 4～5 美元，是命中时的 40 倍；那两天这个仓库所有会话的这类重写共约 430 万 token。所以能开新会话时，只带清单、没通过的测试、已定的决定和分支开新会话接手，不唤醒旧会话。
- **状态记在文件里，进度一屏答，要用户时发通知**（v2.0.0）。主会话上下文 A 线从 7 万涨到 57 万、C 线 3.7 小时涨到 47 万，A 线的 PR 汇报里把两块的审查轮数记错了。所以每块的阶段、已用预算、已定的决定、每条发现的去向记在状态文件里（放在哪见下一条），压缩后先读、汇报照它写。两次协调用户都问过进度；C 线最后一张卡片等了 11 小时，所以要用户拍板时用 `PushNotification` 提醒。
- **状态文件放在插件数据目录，以会话编号命名**（v3.3.0，用户的决定）。原来放在草稿目录，随会话一起被清掉：2026-11-02 复盘重写后的 8 次协调时，状态文件一份也没剩下，只能翻原始会话记录，而本 plugin 改 skill 恰恰要靠真实协调的证据。文件名用会话编号，能和 `~/.claude/projects/` 下的会话记录对上，所以等用户多久这类要靠时间戳的数据不另记。结案时补上终态和 PR 链接；Codex 每次分派的用时和用量也记进去，衡量开发交给 Codex 省了多少要用。路径里的两个变量由 Claude Code 在调用 skill 时替换成实际路径（2.1.309 的实现里确认过，官方的 project-artifact plugin 也这样写）。
- **汇报先写是否结案，提到的东西先说清是什么**（v3.3.0，用户的决定）。重写后的协调里，用户两次问「任务结束了吗？可以归档了吗？」：一次主会话刚汇报完一次真实验证的结果，没提 PR 还没合；一次说了等 CI 通过后自动合并，一小时后用户仍不知道合了没有。平台要求的收尾总结也没防住。用户还至少 5 次追问主会话说的东西指什么：「哪两个邮箱？」「『默认，你改过』是什么？」「录真实回包是什么？」「什么数据库？」「没看懂共用的手动密码的机制」，都是设计文档、任务卡里的说法或没说清的指代；用户全局规则只管代码里的名字，管不到这些。
- **清理审查遗留问题是同一个 skill 的另一种用法**（v2.0.0，用户的决定）。不修的发现都进遗留 Issue（A 线 33 条、C 线 62 条没修），不定期清理只会越积越多。清理时先对照最新主分支复核、关掉过时的，再按根源归类，反复出现的类一处收口并加自动检查，教训写回设计文档或项目规则，让后面的开发会话一开始就避开。
- **开发可以交给 Codex**（v3.0.0，用户的决定）。按 API 价格折算以往 lead 协调的记录，开发会话约占 Claude 用量的八成，主会话和审查各约一成。所以用户说明时才把开发改给本机的 Codex 命令行，审查和整合审查留在 Claude：审查只占一成，换一家模型来审还能发现开发模型自己的盲点。几处做法参考了另一个把任务交给 Codex 的 skill 的实测：Claude 的额度主要消耗在模型调用次数上（每调用一次都要把整份上下文重新读一遍），分派任务本身只占一成左右，分派之后的零碎步骤占四到五成，被唤醒后只回复一句话的回合占两成多，所以检查和自动返工放进 `codex.sh`，全部完成后才唤醒主会话一次，被唤醒的那一回合把该做的事一并完成；Claude 自己排查小问题，消耗了单独完成这件事所需额度的三到五成，所以问题一律交回 Codex；任务书不写规模时，Codex 为一个配置错误写了近 200 行，所以任务书写明规模和禁区。那个 skill 遇到全量测试中失败、单独重跑能通过的用例，直接按偶发放行，这里没有采用：也可能是这次改动让测试互相干扰，交回 Codex 判断并写进汇报。Codex 由脚本随时启动，不受「只有用户那一轮能开会话」的限制，所以开发不预开。不管用户的 Codex 设置是不是完全放开，脚本都只给只读或只能写工作副本的沙箱，提交由主会话做。开发和修复默认允许联网（v3.1.0，用户的决定）；只读那一轮不联网，因为 Codex 的只读沙箱没有联网开关。依赖仍由主会话在沙箱外装好：实测沙箱写不了工作副本以外的缓存目录。Codex 运行期间无法与主会话对话，所以验收清单单独用一轮只读模式提交，确认后在同一个会话里续接开发。Codex 出错或额度用完时停下并通知用户，不自动改用 Claude：悄悄换回 Claude，会消耗用户想节省的额度。尚未在真实协调中使用；已在本机用真实的 Codex 验证整条流程：以只读模式提交方案，在同一个会话里续接修改代码，检查未通过时自动返工后通过，三轮分别运行在只读和只能写工作副本的沙箱里。
- **每块只跑这块的检查，全量合并后跑一次**（v4.1.0，用户的决定，取代 v3.0.0 起「分派开发和修复时带上全量检查」）。2026-11-03 一次真实协调里开发交给了 Codex：项目规定并行开发时各块只跑静态检查和相关测试、合并后由主会话统一跑全量，skill 却要每块跑全量，三块各跑了两三轮，每轮 20 多分钟（改到公共配置时「相关测试」会自动升级成全量），没过就自动交回 Codex 返工，整体拖慢一个多小时。现在 `--verify` 和主会话核实（第 4、6 步）都用项目规矩给开发会话规定的那一档，没规定时用静态检查加这块新写、改过的测试；全量放在第 8 步合并后，和整合审查同时跑，查出的问题交整合修复。Codex 的沙箱常起不了数据库这类服务，跑不了的测试由主会话在沙箱外跑。
- **`codex.sh --stop` 让运行中的任务干净停下**（v4.1.0，用户的决定）。同一次协调里用户中途改了流程，主会话只好临时写脚本盯着运行目录里的阶段、在 Codex 返工写完后杀进程，脚本还在 zsh 下写错了一次（变量没按空格拆开）。停止入口只留下停止请求：Codex 正在写代码的，等这一轮写完、在检查或下一轮返工之前停下（中途杀掉会留下写了一半的工作副本）；正在检查的，检查跑在单独的进程组里，连同子进程立即停掉，5 秒内没停干净再强制结束。停下后在运行目录里写 `stop_note`，分派命令以退出码 5 结束，主会话照常被唤醒一次。已用替身 codex 在写代码中、返工中、检查中（含忽略 TERM 的检查）几种情况下测过；尚未在真实协调中使用。
- **Codex 开发期间心跳保活**（v3.2.0，用户的决定）。实测 Codex 一次分派有时超过一小时，主会话的提示缓存过期后，被唤醒时要重写整份上下文。心跳时不调用工具：调用工具后，桌面端要把结果交回模型再调用一次，这一回合就读两次缓存（以往会话记录里，后台命令启动 1 秒后又有一次读满缓存的调用）。所以计时器在分派时成批启动，不在心跳时重新启动。没有用 Monitor：它最长 30 分钟就失效，续期要调用工具。只用 Codex 审查时不设心跳（v4.0.0，用户的决定）：审查很快。
- **默认开发用 Claude、审查用 Codex**（v4.0.0，用户的决定，取代 v3.0.0 起「开发默认用 Claude、审查留在 Claude」）。仍是换一家模型来审；开发交给 Codex 时审查改回 Claude，用户也可以说明审查用 Claude（如本机没装 Codex）。审查走 Codex 自带的审查模式（`codex exec review`），和 Claude 审查会话「第一步调用 `code-review`」同理：用审查方自己的审查流程，不让它手工审。这个模式下 `--base` 不能和自定义的审查要求同时用，所以审查范围写在任务书里；验收清单、红线、已定的决定由主会话写进任务书，发现的写法由 `codex.sh` 追加的固定规矩交代。审查跑在 Codex 的审查子会话里，`--json` 事件里的用量全是 0，脚本从 `~/.codex/sessions` 下这个子会话自己的记录（`parent_thread_id` 是这次的会话编号）读真实用量。审查默认交给 Codex 后，开工时不再为审查预开会话；Codex 出错时停下通知用户，不自动改开 Claude 审查会话（被子会话唤醒的那一轮也开不了）。尚未在真实协调中使用；已在本机用真实的 Codex 验证：审查在只读沙箱里运行，按任务书里的验收清单逐条核对，三条发现都带位置、出错场景和违反的条目，还指出了断言过松的测试；low 思考强度下审十来行的改动约 20 秒。
- **只能手动调用**（v1.5.0，用户的决定）。skill 开头加了 `disable-model-invocation: true`：只在用户输入 `/agent-team:lead` 时启用，说「开个团队」之类的话不触发，简介也不占每个会话的上下文。小改动走拆分、派活、审查这一整套，来回花的时间和 token 常比改动本身还多，是否开团队交给用户判断。
- **子会话之间不直接通信**，统一经主会话中转：只有主会话掌握全局。
- **保持精简**。新增规则要有真实 session 里观察到的失败作为依据；能交给模型现场判断的边界情况不写。

## Pull Request 要求

- **一个 PR 一个问题**，不要把重构和功能捆在一起。
- **描述它解决的问题**，不只是描述改动：要有真实事件、错误或协调失败的经过。
- **改 skill 内容要有证据**：至少在一次真实的并行子会话协调里走过改动的路径，在 PR 里给出改动前后的行为，最好附会话记录。
- **不要编造**：问题描述和工具行为必须与真实会话、当前工具说明一致。
- **diff 保持最小**，越小越容易验证。
